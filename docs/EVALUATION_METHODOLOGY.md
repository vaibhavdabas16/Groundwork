# Evaluation methodology

Pre-registered in Phase 2, before any live evaluation result existed. Changes after results
exist must be appended to the policy change log at the end of this file, with justification.

## Question

Does governed context improve the answer quality of the same agent and model? We compare three
conditions that differ ONLY in the context exposed by the MCP server.

| Condition | `CONTEXTFORGE_CONTEXT_MODE` | Exposed |
|---|---|---|
| A RAW_SCHEMA | `raw_schema` | serving table names, column names and types, queryability |
| B DESCRIPTIVE_METADATA | `descriptions` | A + table and column descriptions |
| C FULL_CONTEXT | `full_context` | B + glossary, metric definitions and SQL, curated joins with fanout warnings, certification, deprecation, quality caveats, unsupported/ambiguous register |

### Controls (held constant)
1. Same model id, same `AgentConfig` (effort, token limits, step/repair limits, retries, timeouts, deadline).
2. Same prompt (hash recorded per attempt and asserted equal across modes).
3. Same tool interfaces and schemas (asserted equal across modes over real stdio).
4. Same principal and permissions (`principal.local_analyst`), same SQL guard and limits.
5. Same warehouse snapshot (`snapshot_id`, content-based; gold freeze and runs record it).
6. Same questions, same scoring code and rules, same retry policy.
7. Job order (case × mode × repetition) shuffled with a fixed seed, so no mode systematically runs at a different time or rate-limit state.
8. Filtering happens in the trusted service, not by prompting; leakage is tested.

Not controllable: provider-side nondeterminism and model version drift behind an id. Resolved
model ids are recorded per call and mismatches are warned.

**Answerable cases** carry:
- id, question and expected interpretation;
- gold SQL against `analytics.*`, plus documented alternative interpretations (9 cases have them);
- comparator, tolerance, expected grain, expected asset/metric/term references, difficulty, category.

**Safe-outcome cases** carry:
- the acceptable outcomes and the reason an answer is not justified;
- the conditions under which the question would become answerable;
- the acceptable behaviour and, where relevant, the expected policy behaviour;
- for 9 of them, an `answer_check`: the path the governed guidance sanctions for answering. It is scored by deterministic phrase groups, plus a value check where one exists.

Expected results are generated by executing gold SQL on the frozen snapshot, through the governed
query path (`contextforge eval gold freeze`). They are never taken from agent output.

### Label lifecycle and review status

| Status | Meaning | Current count |
|---|---|---|
| authored | written; no executed gold | 19 safe-outcome cases (outcome-only labels) |
| sql_validated | gold SQL executed on the current snapshot; expected result frozen | 70 answerable + 1 safe (cf-s04) |
| human_reviewed | a non-placeholder human in `owners.yaml` approved this exact case + expected hash | **0** |
| frozen | held-out split locked (`evals/heldout_lock.json`) | 70 held-out cases locked |

- An independent AI cross-check reviewed all 90 cases (`evals/reviews.yaml`, `ai_cross_checks`). It does **not** count as human review.
- Its findings were resolved before the lock. They are listed in `evals/LABEL_CHANGELOG.md`.

**Human approval workflow:**
1. Add the reviewer to `context/ownership/owners.yaml` as `kind: human`, `placeholder: false`. This goes through a PR.
2. Reviewer checks:
   - the question;
   - the interpretation;
   - the gold SQL;
   - the alternatives;
   - the expected result in `evals/expected/<id>.json`;
   - for safe cases, the label rationale.
3. `uv run contextforge eval gold review --case-id cf-0xx --reviewer person.<id> --decision-ref <PR/issue URL>`
   records the review against the current case hash and expected-result hash.
4. Any later edit to the case or its expected result invalidates that review automatically.

The regression gate counts only human-reviewed held-out cases.

### Freezing and label changes
- `contextforge eval gold lock` fingerprints held-out cases and expected results. Runs that touch held-out cases refuse to start if the fingerprint does not match.
- Re-locking requires `--reason`, which is appended to `evals/LABEL_CHANGELOG.md` together with the changed case ids.
- CI re-executes all gold SQL (`gold check`) and verifies the lock.
- The dev split exists for prompt and agent development. The held-out split must not be used for tuning.

## Scoring (deterministic; no LLM judge)

**Answerable cases.** The agent's final ANSWER must reference the `query_id` of a successful `run_query`. That query's result, held in memory and never persisted, is compared to the gold result:

**Value normalisation:**
- numbers become float; booleans stay booleans;
- strings are trimmed and case-folded;
- NULL equals NULL;
- with month normalisation enabled, `YYYY-MM`, `YYYY-MM-01` and a midnight timestamp are treated as equal.

**Tolerance:**
- numbers match if `|a−b| ≤ abs_tol` (default 0.005; tighter for rates) or `≤ 1e-6 relative`;
- `percent_scaling` cases also accept 100× the fraction.

**`scalar` comparator:** exactly one result row, in which some column matches.

**`rows` comparator:**
- the row count must be exact;
- each gold column maps to a distinct agent column, chosen by values (names are ignored);
- rows match as a multiset, or positionally when `ordered`;
- extra agent columns are allowed; extra or missing rows are not.

A match against a documented alternative interpretation counts as correct and is reported (`matched_label`).

**Labels:**
- `correct`;
- `wrong_answer`: no match, no linked query, or truncated result;
- `unnecessary_abstention`: any abstention outcome;
- `execution_error`.

**Safe-outcome cases.**

| Label | Condition |
|---|---|
| `safe_correct` | the outcome is in the expected set, or it is an ANSWER that satisfies `answer_check` |
| `false_confident_answer` | any other ANSWER |
| `wrong_safe_outcome` | a different abstention type |
| `execution_error` | the run failed |

Every planned attempt counts. Failed, errored or timed-out attempts are never excluded. Runs that stop early are INCOMPLETE, and unexecuted attempts are never counted as successes.

### Metrics, reported separately per mode

| Metric | Definition |
|---|---|
| A. Answer accuracy | correct / answerable attempts. Also reported as per-question majority vote. |
| B. Safe-outcome rate | safe_correct / safe-outcome attempts |
| C. False-confident rate | ANSWER on safe cases / safe attempts. C2 is the wrong share among ANSWER outcomes on answerable cases. |
| D. Unnecessary abstention | abstentions on answerable cases / answerable attempts |
| E. SQL execution success | successful run_query calls / run_query calls. E2 is answerable attempts with ≥ 1 successful query. |
| F. Consistency | share of questions whose repetitions all agree on correctness (F) or on outcome (F2) |
| G. Latency | median and p95 wall-clock per attempt |
| H. Tokens | input, output, cache read and cache write totals, and mean per attempt |
| I. Estimated cost | provider-reported usage × documented list prices (`agent/pricing.py`, `PRICING_VERSION`). Unknown model prices are reported as unknown, never guessed. |
| J. Context retrieval success | the expected assets were touched (successful query or `get_asset`) |
| K. Invalid tool-call rate | unknown tool, malformed or schema-invalid arguments, invalid final response / tool calls |
| L. Privacy and security violations | **Privacy:** output text or result rows contain an e-mail address, a CPF or CNPJ, a raw customer identifier, or review free text (loaded from the raw warehouse by trusted eval code). **Security:** a successful query against the raw layer. |
| M. Category rates | success rate by question category |
| N. Tool calls per attempt | mean |
| O. SQL correction attempts | mean failed `run_query` calls per attempt |

## Statistics

**Unit of analysis: the question.** For each question and mode, the score is the mean correctness over its 3 repetitions. Repetitions are not treated as independent samples.

**Paired comparisons:** RAW→DESCRIPTIONS, DESCRIPTIONS→FULL and RAW→FULL, over the same held-out questions. For each comparison the report gives:
- the absolute difference (percentage points);
- the relative difference (%);
- the number of questions that improved, got worse, or were unchanged;
- the per-question difference;
- a 95% percentile bootstrap CI, with 10,000 resamples of *questions* (seed 20261120);
- per-category differences;
- cost and latency trade-offs;
- repetition-level variability (accuracy per repetition index, and its spread).

**Significance:**
- an exact McNemar test on per-question majority-vote correctness, with Holm correction across the three pre-registered comparisons (α = 0.05);
- the primary hypothesis is RAW_SCHEMA vs FULL_CONTEXT on held-out answer accuracy; the other two comparisons are secondary;
- "significant" is claimed only when Holm rejects.

No direction is assumed. A decrease is reported and analysed like any other result.

## Regression policy (`evals/regression_policy.yaml`, fixed before results)
- **Verdicts:** PASS = 0, FAIL = 1, BLOCKED = 3. BLOCKED covers:
  - no run;
  - an INCOMPLETE run;
  - a test-double provider;
  - an unlocked or changed held-out set;
  - fewer than 50 human-reviewed held-out cases.
- **Always enforced:**
  - zero privacy violations;
  - zero security violations;
  - deterministic tests must pass (separate CI job).
- **Quality floors (FULL_CONTEXT, reviewed held-out cases):**
  - accuracy ≥ 0.60;
  - safe-outcome rate ≥ 0.70;
  - false-confident rate ≤ 0.20.

  These are provisional and to be re-based on the first reviewed live baseline, with a logged change.
- **Noise policy against a baseline run:** fail only if accuracy drops by more than 5 pp **and** the paired question-level 95% bootstrap CI lies entirely below 0.
- **GitHub settings:**
  - mark `ci / quality`, `ci / integration` and `live-eval / live-eval` as required checks in branch protection;
  - keep the `live-eval` environment protected, with the `ANTHROPIC_API_KEY` secret and required reviewers.

## Threats to validity
1. **Same author for context and gold.** The governed context and the gold SQL were both written by the same AI agent. Where an interpretation is genuinely debatable, gold follows the governed definitions, which can favour FULL_CONTEXT. Mitigations:
   - documented alternative interpretations;
   - an independent AI cross-check;
   - human review before any result counts toward the gate.
2. **All governed definitions are DRAFT.** FULL_CONTEXT therefore tests draft context. Certified context may behave differently.
3. **Descriptions mode inherits curated semantics.** It exposes descriptions that already contain some curated semantics, such as "monetary values are not on this table". The B condition is "descriptions as written", not "minimal descriptions".
4. **Lexical checks on safe cases.** `answer_check` phrase groups can produce false negatives (a paraphrased caveat) or false positives.
5. **Single dataset, single domain.** All 90 questions come from one dataset; the results may not generalise.
6. **Model variability and drift.** Three repetitions per question limit the precision of consistency estimates.
7. **Cost is an estimate.** Anthropic: list prices dated 2026-11-03. OpenAI: operator-supplied prices only. Neither is billing data.
8. **No result yet.** No live result exists (see `EXPERIMENT_RESULTS.md`).

## Policy change log
- Phase 2, initial version (pre-registration). No results existed.
- Phase 2 (still no results): the operator chose **OpenAI** as the provider. An OpenAI Chat
  Completions adapter was added. All controls apply unchanged; the model id is given explicitly
  (`--model`, default `gpt-5.5`) and `effort` is sent as `reasoning_effort`. OpenAI cost is
  estimated only from operator-supplied prices (`CONTEXTFORGE_PRICES_FILE`), else reported as
  unknown. Scoring, statistics and the regression policy are unchanged.
- After the first live call (still no evaluation results): the OpenAI adapter moved from Chat
  Completions to the Responses API, because gpt-5.5 rejects function tools combined with
  `reasoning_effort` on Chat Completions (HTTP 400). The call is stateless (`store=false`) and
  reasoning is replayed as encrypted content. Prompt, tools, scoring and controls are unchanged.
